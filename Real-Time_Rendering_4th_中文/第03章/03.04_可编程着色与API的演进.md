# 3.4 可编程着色与API的演进

来源：《Real-Time Rendering, Fourth Edition》，书页 37—41（PDF 物理页 58—62）。

可编程着色框架的思想可以追溯到 1984 年 Cook 提出的着色树（shade trees）[287]。图 3.4 展示了一个简单的着色器及其对应的着色树。RenderMan 着色语言 [63, 1804] 于 20 世纪 80 年代末从这一思想发展而来。时至今日，它仍与其他不断演进的规范一起用于电影制作中的渲染，例如开放着色语言（Open Shading Language，OSL）项目 [608]。

图 3.4. 一个简单铜材质着色器的着色树，以及与之对应的着色语言程序。（据 Cook [287] 改编。）

消费级图形硬件最早由 3dfx Interactive 于 1996 年 10 月 1 日成功推出。图 3.5 给出了从这一年开始的时间线。其 Voodoo 显卡能够以高质量和高性能渲染游戏《Quake》，因此迅速得到采用。这种硬件从头到尾实现的都是固定功能流水线。在 GPU 原生支持可编程着色器之前，人们曾多次尝试通过多个渲染通道实时实现可编程着色操作。1999 年，《Quake III: Arena》的脚本语言成为这一领域首个得到广泛应用的商业成功案例。正如本章开头所述，NVIDIA 的 GeForce256 是首款被称为 GPU 的硬件，但它并不可编程。不过，它是可配置的。

![图 3.5 部分 API 与图形硬件发布时间线](https://raw.githubusercontent.com/ahuibo/Real-Time-Rendering-4th-CN/main/Real-Time_Rendering_4th_%E4%B8%AD%E6%96%87/assets/fig_3_4_3.5.png)

图 3.5. 部分 API 和图形硬件的发布时间线。

2001 年初，NVIDIA 的 GeForce 3 成为首款支持可编程顶点着色器的 GPU [1049]，这些功能通过 DirectX 8.0 和 OpenGL 扩展提供。这些着色器使用一种类似汇编的语言编写，由驱动程序即时转换为微代码。DirectX 8.0 也包含像素着色器，但这些像素着色器还算不上真正可编程：它们所支持的有限“程序”会由驱动程序转换成纹理混合状态，再由这些状态把硬件“寄存器组合器”连接起来。这些“程序”不仅长度有限（最多 12 条指令），还缺少重要功能。Peercy 等人 [1363] 通过研究 RenderMan，确定了依赖纹理读取和浮点数据对于真正的可编程性至关重要。

当时的着色器不允许使用流程控制（分支），因此必须把条件判断的两个分支都计算出来，再选择其中一个结果或在两者之间插值，以此模拟条件判断。DirectX 定义了着色器模型（Shader Model，SM）这一概念，用来区分具有不同着色器能力的硬件。2002 年，包含着色器模型 2.0 的 DirectX 9.0 发布，提供了真正可编程的顶点着色器和像素着色器。OpenGL 也通过各种扩展提供了类似功能。新版本加入了对任意依赖纹理读取以及 16 位浮点值存储的支持，终于满足了 Peercy 等人确定的全部要求。指令、纹理和寄存器等着色器资源的上限得到提高，使着色器能够实现更复杂的效果。此外，还加入了对流程控制的支持。着色器的长度和复杂度不断增加，使汇编编程模型变得越来越繁琐。幸运的是，DirectX 9.0 还包含了 HLSL。这种着色语言由 Microsoft 与 NVIDIA 合作开发。大约在同一时期，OpenGL ARB（架构审查委员会，Architecture Review Board）发布了 GLSL，这是一种用于 OpenGL、与 HLSL 相当类似的语言 [885]。这些语言深受 C 编程语言的语法和设计理念影响，也包含了来自 RenderMan 着色语言的元素。

着色器模型 3.0 于 2004 年推出，增加了动态流程控制，大幅增强了着色器的能力。它还把可选功能变成了必需功能，进一步提高了资源上限，并为顶点着色器中的纹理读取增加了有限支持。当新一代游戏主机分别于 2005 年末（Microsoft 的 Xbox 360）和 2006 年末（Sony Computer Entertainment 的 PLAYSTATION 3 系统）推出时，它们都配备了着色器模型 3.0 级别的 GPU。Nintendo 的 Wii 主机于 2006 年末首次发售，其 GPU 是最后一批引人注目的固定功能 GPU 之一。到如今，纯粹的固定功能流水线早已成为过去。着色器语言的发展已达到可以使用多种工具来创建和管理它们的程度。图 3.6 展示了其中一种工具的屏幕截图，它采用了 Cook 的着色树概念。

可编程性方面的下一次重大进步同样出现在 2006 年末前后。DirectX 10.0 [175] 所包含的着色器模型 4.0 引入了若干重要功能，例如几何着色器和流输出。着色器模型 4.0 为所有着色器（顶点、像素和几何着色器）提供了统一的编程模型，也就是前文所述的统一着色器设计。资源上限进一步提高，同时加入了对整数数据类型（包括按位运算）的支持。OpenGL 3.3 中引入的 GLSL 3.30 提供了类似的着色器模型。

2009 年，DirectX 11 和着色器模型 5.0 发布，增加了曲面细分阶段的着色器和计算着色器，后者也称为 DirectCompute。这一版本还着重更有效地支持 CPU 多处理，这个主题将在第 18.5 节讨论。OpenGL 在 4.0 版本中增加了曲面细分，在 4.3 版本中增加了计算着色器。

DirectX 和 OpenGL 的演进方式不同。两者都会为特定版本设定所需的硬件支持级别。Microsoft 掌控着 DirectX API，因此会直接与 AMD、NVIDIA、Intel 等独立硬件厂商（IHV），以及游戏开发商和计算机辅助设计软件公司合作，决定开放哪些功能。OpenGL 由硬件和软件厂商组成的联盟开发，并由非营利组织 Khronos Group 管理。由于参与公司众多，API 功能往往在 DirectX 中引入一段时间之后，才会出现在某个 OpenGL 版本中。不过，OpenGL 允许使用厂商专有的或更通用的扩展，使最新的 GPU 功能能够在正式版本提供支持之前就得到使用。

API 的下一次重大变革由 AMD 于 2013 年推出 Mantle API 引领。Mantle 与电子游戏开发商 DICE 合作开发，其理念是去掉图形驱动程序的大量开销，并将这部分控制权直接交给开发者。在进行这种重构的同时，它还进一步支持高效的 CPU 多处理。这一新类别的 API 着重于大幅减少 CPU 花费在驱动程序中的时间，并为 CPU 多处理器提供更高效的支持（第 18 章）。Microsoft 采纳了 Mantle 开创的理念，并于 2015 年以 DirectX 12 的形式发布。注意，DirectX 12 并不以开放新的 GPU 功能为重点：DirectX 11.3 开放了相同的硬件功能。这两个 API 都可以用来向 Oculus Rift 和 HTC Vive 等虚拟现实系统发送图形。不过，DirectX 12 对 API 进行了彻底的重新设计，使其能更好地映射到现代 GPU 架构。对于 CPU 端驱动程序开销造成瓶颈的应用，或者能通过使用更多 CPU 处理器执行图形工作来提高性能的应用，低开销驱动程序很有用 [946]。从较早的 API 移植过来可能很困难，而简单直接的实现反而可能导致性能下降 [249, 699, 1438]。

Apple 于 2014 年发布了自己的低开销 API，名为 Metal。Metal 最初可用于 iPhone 5S 和 iPad Air 等移动设备，一年后，较新的 Macintosh 计算机通过 OS X El Capitan 也获得了支持。除了提高效率，减少 CPU 使用量还能节省电能，这在移动设备上是一个重要因素。这个 API 有自己的着色语言，同时面向图形程序和 GPU 计算程序。

AMD 将其 Mantle 的开发成果捐赠给了 Khronos Group，后者于 2016 年初发布了自己的新 API，名为 Vulkan。与 OpenGL 一样，Vulkan 可以在多种操作系统上运行。Vulkan 使用一种名为 SPIR-V 的新高级中间语言，它既用于表示着色器，也用于通用 GPU 计算。预编译的着色器具有可移植性，因此可以用于任何支持其所需能力的 GPU [885]。Vulkan 也可用于非图形的 GPU 计算，因为它不需要显示窗口 [946]。Vulkan 与其他低开销驱动程序之间的一个显著区别是，它旨在适用于广泛的系统，从工作站到移动设备都包含在内。

在移动设备上，通常使用的是 OpenGL ES。“ES”是嵌入式系统（Embedded Systems）的缩写，因为这一 API 在开发时就考虑到了移动设备。当时，标准 OpenGL 相当臃肿，其某些调用结构也比较缓慢，还要求支持很少使用的功能。OpenGL ES 1.0 于 2003 年发布，是 OpenGL 1.3 的精简版本，描述的是固定功能流水线。虽然 DirectX 的发布时机与支持它的图形硬件相配合，但移动设备图形支持的发展并不是以同样的方式进行的。例如，2010 年发布的第一代 iPad 实现的是 OpenGL ES 1.1。2007 年，OpenGL ES 2.0 规范发布，提供了可编程着色功能。它基于 OpenGL 2.0，但不包含固定功能部分，因此不向后兼容 OpenGL ES 1.1。OpenGL ES 3.0 于 2012 年发布，提供了多渲染目标、纹理压缩、变换反馈、实例化以及种类丰富得多的纹理格式和模式等功能，还改进了着色器语言。OpenGL ES 3.1 增加了计算着色器，3.2 则增加了几何着色器、曲面细分着色器及其他功能。第 23 章将更详细地讨论移动设备架构。

OpenGL ES 的一个分支是基于浏览器的 API WebGL，它通过 JavaScript 调用。这个 API 的第一个版本于 2011 年发布，可以在大多数移动设备上使用，因为其功能等同于 OpenGL ES 2.0。与 OpenGL 一样，扩展可以让开发者使用更高级的 GPU 功能。WebGL 2 以支持 OpenGL ES 3.0 为前提。

WebGL 特别适合用于功能实验或课堂教学：

- 它是跨平台的，能够在所有个人计算机和几乎所有移动设备上运行。
- 驱动程序的认可由浏览器负责。即使某个浏览器不支持特定的 GPU 或扩展，另一个浏览器通常也会支持。
- 代码采用解释执行而非编译执行，开发时只需要一个文本编辑器。
- 大多数浏览器都内置调试器，而且可以查看任何网站上运行的代码。
- 例如，可以通过把程序上传到网站或 Github 来部署程序。

three.js [218] 等更高层次的场景图与效果库，让人们能够方便地使用各种较复杂效果的代码，例如阴影算法、后处理效果、基于物理的着色以及延迟渲染。
