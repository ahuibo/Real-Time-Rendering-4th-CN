# 18.2 定位瓶颈

来源：原书第 786—788 页（PDF 第 807—809 页）。本节范围从 18.2 标题起，至 18.3 标题前，包含 18.2.1—18.2.5 全部小节。

优化流水线的第一步，是定位最大的瓶颈 [1679]。寻找瓶颈的一种方法是设计若干项测试，每项测试都减少某个特定阶段所执行的工作量。如果其中一项测试使每秒帧数上升，就找到了瓶颈所在的阶段。另一种相关的方法，是减少其他阶段的工作负载，同时保持被测试阶段的工作负载不变。如果性能没有变化，那么工作负载未改变的那个阶段就是瓶颈。性能分析工具能够详细指出哪些 API 调用开销较大，却不一定能准确指出流水线中究竟是哪个阶段拖慢了其他阶段。即使工具能够指出，理解每项测试背后的思路仍然很有帮助。

下面简要讨论测试各个阶段时采用的一些思路，让读者了解这类测试如何进行。统一着色器架构的出现，就是说明理解底层硬件有多么重要的一个绝佳例子。自 2006 年底起，许多 GPU 都以这种架构为基础。其思想是让顶点着色器、像素着色器及其他着色器使用同一组功能单元。GPU 负责负载均衡，调整分配给顶点着色与像素着色的单元比例。例如，渲染一个很大的四边形时，可能只需要给顶点变换分配少量着色器单元，而将大多数单元用于片元处理。这样一来，要准确判断瓶颈位于顶点着色器阶段还是像素着色器阶段，就不那么直观了 [1961]。不过，瓶颈仍然会是整体的着色器处理，或者某个其他阶段，因此我们将依次讨论各种可能性。

## 18.2.1 测试应用阶段

如果所使用的平台提供了测量处理器工作负载的实用工具，就可以用它检查程序是否占用了 100%（或接近 100%）的 CPU 处理能力。如果 CPU 始终处于忙碌状态，程序很可能受限于 CPU。不过，这种判断并非总是可靠，因为应用程序有时可能正在等待 GPU 完成一帧。我们虽然会说程序受限于 CPU 或 GPU，但在一帧的整个处理过程中，瓶颈可能发生变化。

测试 CPU 限制的一种更巧妙的方法，是向 GPU 提交只会让它执行很少工作、甚至不执行任何工作的数据。在某些系统上，只需用空驱动程序（接受调用却什么也不做的驱动程序）替代真正的驱动程序，就能实现这一点。这样实际上就确定了整个程序运行速度的上限，因为既不使用图形硬件，也不调用真正的驱动程序，因此运行在 CPU 上的应用部分始终是瓶颈。通过这项测试，可以了解那些不在应用阶段中运行、而是基于 GPU 的阶段还有多大的改进空间。不过需要注意，使用空驱动程序也可能掩盖由驱动程序本身的处理，以及 CPU 与 GPU 之间的通信所造成的瓶颈。驱动程序往往可能是 CPU 端瓶颈的成因，后面我们会深入讨论这一话题。

另一种更直接的方法，是在条件允许时降低 CPU 的时钟频率 [240]。如果性能随着 CPU 频率的降低而按比例下降，那么应用程序至少在一定程度上受限于 CPU。同样的降频方法也可用于 GPU。如果降低 GPU 速度后性能下降，那么应用程序至少在部分时间内受限于 GPU。这些降频方法有助于识别瓶颈，但有时也会使原本不是瓶颈的阶段变成瓶颈。另一个选择是超频，不过可别说你是在这里读到这个建议的。

## 18.2.2 测试几何处理阶段

几何阶段是最难测试的阶段。这是因为，改变这一阶段的工作负载时，其他两个阶段中的一个或两个的工作负载往往也会随之改变。为避免这一问题，Cebenoyan [240] 给出了一系列测试，从光栅化器的各阶段开始，沿流水线向上游逐步测试。

几何阶段主要有两个可能出现瓶颈的环节：顶点获取和顶点处理。要判断瓶颈是否来自物体数据传输，可以增大顶点格式的大小。例如，可以为每个顶点额外传送几组纹理坐标。如果性能下降，那么这个环节就是瓶颈。

顶点处理由顶点着色器完成。针对顶点着色器瓶颈的测试，是增加着色器程序的长度。这里需要小心，确保编译器不会把这些额外指令优化掉。

如果流水线还使用了几何着色器，那么它们的性能取决于输出大小和程序长度。如果使用了曲面细分着色器，程序长度同样会影响性能，曲面细分因子也会产生影响。在避免改变其他阶段工作量的前提下，调整上述任一因素，都有助于判断其中是否存在瓶颈。

## 18.2.3 测试光栅化阶段

这一阶段包括三角形设置和三角形遍历。阴影贴图生成使用极其简单的像素着色器，因此其瓶颈可能出现在光栅化器阶段或合并阶段。尽管通常很少见 [1961]，对于曲面细分产生的小三角形，或草、枝叶等物体中的小三角形，三角形设置和光栅化也有可能成为瓶颈。不过，小三角形也会增加顶点着色器和像素着色器的使用量。给定区域中的顶点更多，显然会增加顶点着色器的负载。像素着色器负载也会增加，因为每个三角形都以一组组 2 × 2 的像素块进行光栅化，所以落在各个三角形之外的像素数量会增加 [59]。这种现象有时称为四像素块过度着色（quad overshading，见第 23.1 节）。要判断光栅化是否确实是瓶颈，可以同时增大顶点着色器和像素着色器的程序长度，以增加它们的执行时间。如果每帧渲染时间没有增加，那么瓶颈就位于光栅化阶段。

## 18.2.4 测试像素处理阶段

可以通过改变屏幕分辨率，测试像素着色器程序的影响。如果降低屏幕分辨率后帧率明显上升，那么像素着色器很可能是瓶颈，至少在部分时间内如此。如果使用了细节层次系统，就需要小心：较小的屏幕也可能使显示的模型得到简化，从而减轻几何阶段的负载。

降低显示分辨率还会影响三角形遍历、深度测试与混合、纹理访问等因素的开销。为排除这些因素并单独定位瓶颈，可以采用与测试顶点着色器程序相同的方法：增加指令，观察它们对执行速度的影响。同样，务必确认编译器没有把这些额外指令优化掉。如果帧渲染时间增加，那么像素着色器就是瓶颈（或者至少在其执行开销增加的过程中，于某个时刻变成了瓶颈）。另一种做法是将像素着色器简化到只包含最少数量的指令，而这在顶点着色器中往往很难做到。如果总渲染时间减少，就找到了一个瓶颈。纹理缓存未命中也可能代价高昂。如果将某个纹理替换成分辨率为 1 × 1 的版本后，性能明显提高，那么纹理内存访问就是一个瓶颈。

着色器是独立的程序，有其自身的优化技术。Persson [1383, 1385] 介绍了若干底层着色器优化方法，还具体说明了图形硬件如何演进，以及最佳实践如何随之变化。

## 18.2.5 测试合并阶段

这一阶段执行深度测试和模板测试，进行混合，并将通过测试后保留下来的结果写入缓冲区。改变这些缓冲区的输出位深，是调整这一阶段带宽开销、观察它是否可能成为瓶颈的一种方法。为不透明物体开启 alpha 混合，或采用其他混合模式，也会影响光栅操作所执行的内存访问量和处理量。

在后处理通道、阴影、粒子系统渲染中，以及在较小程度上的毛发和草的渲染中，这一阶段都可能成为瓶颈，因为这些情况下的顶点着色器和像素着色器很简单，所做的工作很少。
