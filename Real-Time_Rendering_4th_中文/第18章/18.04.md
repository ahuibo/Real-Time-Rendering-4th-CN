# 18.4 优化

来源：《Real-Time Rendering, Fourth Edition》书页 790—805（PDF 物理页 811—826）。本节从 18.4 标题开始，至 18.5 标题前结束；包含全部下级小节、图 18.1—18.7、公式（18.1）—（18.3）及两条脚注。技术陈述与性能数据均保留原书出版时语境。

一旦找到了瓶颈，我们就希望优化那个阶段来提高性能。本节介绍应用、几何、光栅化和像素处理阶段的优化技术。

## 18.4.1 应用阶段

优化应用阶段的方法是加快代码执行，以及加快或减少程序的内存访问。这里讨论一些普遍适用于 CPU 的代码优化要点。

对于代码优化，关键是找出代码中耗时最多的位置。优秀的代码性能分析器对于找到这些耗时最多的代码热点至关重要。随后便在这些位置进行优化。程序中的这类位置往往是内层循环，也就是每帧要执行很多次的代码片段。

优化的基本规则是尝试各种策略：重新审视算法、假设和代码语法，尽可能尝试不同变体。CPU 架构与编译器的表现，往往使人难以凭直觉判断怎样写出最快的代码，因此要质疑自己的假设，并保持开放的态度。

最初应做的事情之一，是试验编译器的优化选项。通常有许多不同选项可供尝试。对于应使用哪些优化选项，尽量少做预设，最好完全不做。例如，让编译器采用更激进的循环优化，反而可能使代码变慢。另外，如果条件允许，也应试试不同编译器，因为它们的优化方式不同，有些明显更优。性能分析器可以告诉你每项改变产生了什么影响。

### 内存问题

多年前，算术指令的数量是衡量算法效率的关键；现在，关键在于内存访问模式。处理器速度的增长远快于 DRAM 数据传输速率的增长，后者受到引脚数量限制。1980—2005 年间，CPU 性能大约每两年翻一番，而 DRAM 性能大约每六年才翻一番 [1060]。这一问题称为冯·诺依曼瓶颈或内存墙。面向数据的设计把缓存连贯性作为优化的重点。注1

在现代 GPU 上，重要的是数据移动的距离。速度与功耗代价和这个距离成正比。缓存访问模式能够造成数量级的性能差异 [1206]。缓存是一小块快速存储区。它之所以有效，是因为程序通常具有很强的连贯性，可供缓存利用。也就是说，内存中相邻位置往往被接连访问（空间局部性），代码也常常按顺序访问。此外，同一内存位置往往会被反复访问（时间局部性），缓存也利用了这一点 [389]。处理器缓存的访问很快，速度仅次于寄存器。许多快速算法都致力于尽可能局部地访问数据，并尽可能减少访问量。

寄存器和本地缓存构成存储层次的一端，接下来依次是动态随机存取存储器（DRAM），再往后是 SSD 和硬盘存储。顶端是少量、快速而昂贵的存储，底端是大量、缓慢而廉价的存储。层次中每下降一级，速度都会按某个明显的倍数下降，见图 18.1。例如，处理器寄存器通常在一个时钟周期内即可访问，而 L1 缓存的访问需要几个周期。每次跨越层级，延迟都会这样增加。如第 3.10 节所述，架构有时可以隐藏延迟，但它始终是必须考虑的因素。

**图 18.1** 存储层次。沿金字塔向下，速度与成本都会降低。

性能分析器很难直接发现不良的内存访问模式。良好的模式必须从一开始就纳入设计 [1060]。下面列出编程时应考虑的一些要点。

- 代码中顺序访问的数据，在内存中也应顺序存放。例如，渲染三角网格时，如果访问顺序是纹理坐标 #0、法线 #0、颜色 #0、顶点 #0、纹理坐标 #1、法线 #1，就应按这个顺序连续存放。对于 GPU，这一点也可能很重要，例如变换后的顶点缓存（第 16.4.4 节）。关于为何把数据存成独立数据流有时更有利，另见第 16.4.5 节。
- 在关键代码中避免指针间接访问、跳转和函数调用，因为它们可能明显降低 CPU 性能。沿着一个指针找到另一个指针，再继续追踪，就会产生指针间接访问。现代 CPU 会尝试推测执行指令（分支预测）并预取内存（缓存预取），使所有功能单元都忙于执行代码。当循环中的代码流保持一致时，这些技术非常有效；面对二叉树、链表和图等分支数据结构时，它们却会失效，因此尽可能改用数组。McVoy 和 Staelin [1194] 给出了通过指针遍历链表的代码示例。这会使前后数据都发生缓存未命中，示例中 CPU 停顿时间超过了沿指针访问本身所需时间的 100 倍——后者是假设缓存能够提供指针地址时的耗时。Smits [1668] 指出，把基于指针的树展平成带跳跃指针的列表，可以显著改进层次遍历。使用 van Emde Boas 布局也是避免缓存未命中的方法，见第 19.1.4 节。高分支度的树往往优于二叉树，因为它们降低树的深度，从而减少间接访问次数。
- 将频繁使用的数据结构对齐到缓存行大小的整数倍，可以显著提高整体性能。例如，Intel 和 AMD 处理器上常见 64 字节缓存行 [1206]。编译器选项会有所帮助，但设计数据结构时就考虑对齐所需的填充（padding）更明智。Windows 和 Linux 上的 VTune、CodeAnalyst，Mac 上的 Instruments，以及 Linux 上的开源 Valgrind 等工具，都能帮助查找缓存瓶颈。对齐也会影响 GPU 着色器性能 [331]。
- 尝试不同的数据结构组织方式。例如，Hecker [698] 对一个简单的矩阵乘法程序试验了多种矩阵结构，节省的时间之多令人意外。对于特定架构，结构体数组：

```cpp
struct Vertex { float x, y, z; };
Vertex myvertices[1000];
```

或者数组结构体：

```cpp
struct VertexChunk { float x[1000], y[1000], z[1000]; };
VertexChunk myvertices;
```

可能表现更好。第二种结构更适合使用 SIMD 指令，但顶点数增多时，缓存未命中的可能性也会上升。随着数组规模增大，混合方案：

```cpp
struct Vertex4 { float x[4], y[4], z[4]; };
Vertex4 myvertices[250];
```

可能是最佳选择。

- 对于大小相同的对象，通常最好在启动时分配一个大内存池，再使用自己的分配和释放例程管理池内内存 [113, 736]。Boost 等库提供了池式分配。连续的一组记录，比单独分配产生的记录更可能具有缓存连贯性。不过，对于 C#、Java 等带垃圾回收的语言，内存池实际上可能降低性能。

虽然这不直接属于内存访问模式问题，但仍值得避免在渲染循环中分配或释放内存。使用内存池，一次性分配临时工作空间，并让栈、数组等结构只增长不缩小，用变量或标志记录哪些元素应视为已删除。

**注1：** 不要把这一研究领域与“数据驱动设计”混淆。后者可以指许多不同的东西，从 AWK 编程语言到 A/B 测试都包括在内。

## 18.4.2 API 调用

本书一直依据硬件的一般发展趋势提出建议。例如，带索引的顶点缓冲区对象，通常是向加速器提供几何数据的最快方式（第 16.4.5 节）。本节讨论怎样最有效地调用图形 API 本身。多数图形 API 的架构相似，已经有一些成熟的方法可供高效使用。

理解对象缓冲区的分配和存储，是高效渲染的基础 [1679]。对于具有 CPU 和独立 GPU 的桌面系统，两者通常各有自己的内存。图形驱动程序一般控制对象的驻留位置，但可以向它提供提示，说明把对象存在哪里最好。常见的分类是静态缓冲区与动态缓冲区。如果缓冲区数据每帧都改变，则最好使用不需要在 GPU 上永久占用存储空间的动态缓冲区。游戏主机、配有低功耗集成 GPU 的笔记本电脑，以及移动设备，通常采用统一内存，即 GPU 与 CPU 共享同一物理内存。即使在这种配置下，在正确的池中分配资源仍然很重要。正确地将资源标记为仅供 CPU 或仅供 GPU 使用，仍可带来好处。一般而言，如果一个内存区域必须被两个芯片共同访问，当其中一个写入时，另一个就必须使自己的缓存失效，确保不会读到过期数据；这是一项昂贵的操作。

如果对象不发生形变，或者形变能够完全由着色器程序完成（例如蒙皮），那么把对象数据存放在 GPU 内存中会很有利。把它存为静态缓冲区，就能表明对象数据不变。这样，每次渲染一帧时就不必再通过总线传输它，从而避免流水线在这里出现瓶颈。GPU 内部的内存带宽通常远高于 CPU 与 GPU 之间的总线带宽。

### 状态改变

调用 API 会产生几种相关开销。在应用端，调用越多，应用耗时越长，无论调用实际做什么。这一开销可能很小，也可能明显，空驱动程序可以帮助识别它。依赖 GPU 数值的查询函数，可能由于与 CPU 同步时的停顿而使帧率减半 [1167]。这里深入讨论一种常见图形操作的优化：准备好流水线以绘制网格。这可能涉及改变状态，例如设置着色器及其 uniform 变量、绑定纹理、改变混合状态或所用颜色缓冲区，等等。

应用提高性能的一种主要方法，是把渲染状态相似的对象分组，从而尽量减少状态改变。GPU 是极其复杂的状态机，甚至可能是计算机科学中最复杂的状态机，因此改变状态可能很昂贵。少量成本可能涉及 GPU，但大部分来自驱动程序在 CPU 上的执行。如果 GPU 与 API 能很好地对应，状态改变的成本往往可预测，尽管仍然不小。如果 GPU 的功耗限制很严格、芯片面积有限（例如某些移动设备），或者需要绕过硬件缺陷，那么驱动程序可能不得不进行复杂的补救，产生出乎意料的高开销。状态改变的成本主要位于 CPU 端的驱动程序中。

一个具体例子是 PowerVR 架构如何支持混合。在旧 API 中，混合通过固定功能式接口指定。PowerVR 的混合是可编程的，这意味着驱动程序必须把当前混合状态补入像素着色器 [699]。在这种情况下，更先进的设计与 API 对应得不好，因而给驱动程序带来明显的设置开销。本章各处都提醒读者，硬件架构及其运行软件会影响各种优化的重要性；对于状态改变开销，这一点尤其如此。甚至具体 GPU 型号和驱动程序版本都可能产生影响。阅读本节时，请想象每页都盖着醒目的红字：“你的实际效果可能不同。”

Everitt 和 McDonald [451] 指出，不同类型的状态改变在成本上差别很大，并大致列出了 NVIDIA OpenGL 驱动程序每秒可以执行其中几种操作的次数。以下是他们在 2014 年给出的顺序，从最昂贵到最便宜：

- 渲染目标（帧缓冲区对象），约 6 万次/秒。
- 着色器程序，约 30 万次/秒。
- 混合模式（ROP），例如用于透明效果的模式。
- 纹理绑定，约 150 万次/秒。
- 顶点格式。
- uniform 缓冲区对象（UBO）绑定。
- 顶点绑定。
- uniform 更新，约 1000 万次/秒。

其他资料也支持这一大致的成本顺序 [488, 511, 741]。还有一种更昂贵的改变，是在 GPU 渲染模式与计算着色器模式之间切换 [1971]。可以对待显示对象排序，先按着色器分组，再按所用纹理分组，依此沿成本顺序向下，从而避免状态改变。按状态排序有时称为批处理。

另一种策略是重组对象数据，让更多数据可以共享。减少纹理绑定改变的一种常见方法，是把多幅纹理图像放进一张大纹理中，或者更好地放进纹理数组。如果 API 支持，无绑定纹理也是避免状态改变的选择（第 6.2.5 节）。相比更新 uniform，更换着色器程序通常较贵，因此一类材质内部的变化，可能更适合通过带有 if 语句的单个着色器来表达。共享着色器也可能让你建立更大的批次 [1609]。不过，让着色器更复杂也可能降低 GPU 性能。通过测量判断什么有效，是唯一可靠的办法。

向图形 API 发出数量更少、作用更大的调用，还能进一步节省开销。例如，多个 uniform 往往可以成组定义和设置，因此绑定单个 uniform 缓冲区对象要高效得多 [944]。在 DirectX 中，它们称为常量缓冲区。正确使用它们，既节省每次函数调用的时间，也节省每个独立 API 调用内部进行错误检查的时间 [331, 613]。

现代驱动程序常常把状态设置延迟到遇见第一个绘制调用时。如果在此之前出现冗余 API 调用，驱动程序就会过滤掉它们，避免实际进行状态改变。通常用脏标志记录需要改变状态，因此每次绘制调用之后都恢复到基础状态，可能很昂贵。例如，准备绘制对象时，你可能希望默认认为状态 X 已关闭。一种实现方式是先执行 `Enable(X); Draw(M1); Disable(X);`，再执行 `Enable(X); Draw(M2); Disable(X);`，这样每次绘制后都会恢复状态。然而，这也很可能在两次绘制调用之间再次设置状态而浪费大量时间，尽管两者之间实际上并不需要改变状态。

应用通常掌握关于何时需要改变状态的更高层信息。例如，从不透明表面的 replace 混合模式切换到透明表面的 over 模式，通常每帧只需要做一次。完全可以避免在每个对象渲染前都设置混合模式。Galeano [511] 表明，如果不进行这种过滤，而发出不必要的状态调用，他们的 WebGL 应用每帧就会多花接近 2 ms。不过，如果驱动程序已经能够高效过滤冗余，那么应用对每个调用重复做同样的检查也可能是浪费。应在过滤 API 调用上投入多少工作，主要取决于底层驱动程序 [443, 488, 741]。

### 合并与实例化

高效使用 API 可以避免让 CPU 成为瓶颈。API 的另一个问题是小批次问题。如果忽视它，它可能成为影响现代 API 性能的重要因素。简单说，渲染少数含有大量三角形的网格，比渲染许多小而简单的网格高效得多。这是因为每个绘制调用都有固定开销，无论图元大小如何，处理图元都要付出这项代价。

早在 2003 年，Wloka [1897] 就表明，每批绘制两个相对较小的三角形时，吞吐量距离被测 GPU 的最大吞吐量相差 375 倍。注2 在 2.7 GHz CPU 上，得到的不是每秒 1.5 亿个三角形，而是每秒 40 万个。若场景由大量小而简单的对象构成，每个仅包含几个三角形，那么性能会完全受 API 在 CPU 上的开销限制；GPU 无法进一步提高它。也就是说，CPU 处理绘制调用的时间，超过 GPU 实际绘制网格所需的时间，使 GPU 得不到足够工作。

Wloka 的经验法则是：“每帧你只能得到 X 个批次。”这是每帧能够发出的绘制调用数的上限，纯粹是由 CPU 成为限制因素造成的。2003 年，API 成为瓶颈的分界点约为每个对象 130 个三角形。图 18.2 显示，到 2006 年，这一分界点升到了每个网格 510 个三角形。时代已经变化。人们做了大量工作来缓解绘制调用问题，CPU 也变得更快。2003 年的建议是每帧 300 次绘制调用；2012 年，一个团队的上限是每帧 16000 次 [1381]。即便如此，对于某些复杂场景，这个数目仍然不够。采用 DirectX 12、Vulkan、Metal 等现代 API，可以把驱动程序本身的开销降得很低，这是它们的一项主要优势 [946]。不过，GPU 对每个网格也可能有自己的固定成本。

**注2：** Wloka 使用 batch 一词表示通过一次绘制调用渲染的单个网格。多年来，这个术语的含义有所扩展，现在有时也表示一组具有相同状态、将要渲染的独立对象，因为这样能降低 API 开销。

减少绘制调用数量的一种方法，是把多个对象合并成一个网格，只需一次绘制调用就能渲染整个集合。对于使用相同状态、且至少相互之间保持静止的一组对象，合并只需做一次，之后每帧都可复用这个批次 [741, 1322]。能够合并网格，也是考虑通过共用着色器和纹理共享技术来避免状态改变的另一个理由。合并带来的节省，不仅来自减少 API 绘制调用，也来自应用本身要处理的对象变少。然而，批次如果远大于所需规模，可能使视锥体剔除等其他算法效率降低 [1381]。一种做法是借助包围体层次结构，查找并分组彼此靠近的静态对象。合并的另一个问题是选择操作，因为所有静态对象在同一个网格中不再有区分。典型解决方案是在网格的每个顶点处保存对象标识符。

尽量减少应用处理与 API 开销的另一种方法，是采用某种实例化形式 [232, 741, 1382]。多数 API 支持通过一次调用将一个对象绘制多次。通常，先指定一个基础模型，再提供独立数据结构，保存每个所需实例的信息。除位置与朝向外，还可以逐实例指定其他属性，例如树叶颜色、受风产生的弯曲程度，或任何可供着色器程序影响模型的参数。大量使用实例化，就能创建郁郁葱葱的丛林场景，见图 18.3。人群场景也非常适合实例化：从一组备选项中选择不同身体部件，可以让每个角色看起来不同。随机着色和贴花还能进一步增加变化。实例化还可以与细节层次技术结合 [122, 1107, 1108]，图 18.4 展示了一个例子。

一种结合合并与实例化的概念称为合并实例化（merge-instancing）：合并后的网格中包含的对象，本身又可以被实例化 [146, 1382]。理论上，几何着色器可以用于实例化，因为它能复制输入网格的数据。实际中，如果需要很多实例，这种方法可能比使用 API 实例化命令更慢。几何着色器的设计意图是对数据进行局部、小规模的扩增 [1827]。此外，在某些架构中，例如 Mali 的分块渲染器，几何着色器由软件实现。引用 Mali 最佳实践指南 [69] 的话：“为你的问题寻找更好的解决办法。几何着色器不是你的解决方案。”

## 18.4.3 几何阶段

几何阶段负责变换、逐顶点光照、裁剪、投影和屏幕映射。本书其他章节讨论了减少流水线中数据量的方法。高效的三角网格存储、模型简化、顶点数据压缩（第 16 章）都能同时节省处理时间和内存。视锥体剔除、遮挡剔除等技术（第 19 章）可以避免把整个图元送入流水线。在 CPU 上加入这些大尺度技术，可以彻底改变应用的性能特征，因此值得在开发早期就尝试。在 GPU 上，这类技术不那么常见。一个值得注意的例子是，可以利用计算着色器执行各种剔除 [1883, 1884]。

光照各项的效果可以逐顶点计算，也可以逐像素计算（在像素处理阶段），或者二者结合。光照计算有多种优化方式。首先应考虑所使用的光源类型。所有三角形都需要光照吗？有时，一个模型只需要纹理、纹理加顶点颜色，或者仅需要顶点颜色。

如果光源相对于几何体保持静止，就可以预计算漫反射光照与环境光照，并将它们作为顶点颜色保存。这通常称为把光照“烘焙”进去。更复杂的预光照形式，是预计算场景中的漫反射全局光照（第 11.5.1 节）。这种光照可以作为顶点颜色、顶点强度或光照贴图保存。

对于前向渲染系统，光源数量会影响几何阶段的性能。光源越多，计算就越多。减少工作量的一种常见方法，是禁用或缩减局部光照，改用环境贴图（第 10.5 节）。

## 18.4.4 光栅化阶段

光栅化可以从几个方面优化。对于封闭的实体对象，以及永远不会露出背面的对象（例如房间内墙壁的背面），应开启背面剔除（第 19.3 节）。这会使需要光栅化的三角形数量大约减半，从而减轻三角形遍历的负担。此外，如果像素着色计算很昂贵，这样做尤其有益，因为背面完全不会被着色。

## 18.4.5 像素处理阶段

优化像素处理往往很有收益，因为通常需要着色的像素远多于顶点。但也存在值得注意的例外。即使一次绘制最终没有产生任何可见像素，顶点也总要处理。如果渲染引擎的剔除不够有效，顶点着色的成本可能超过像素着色。太小的三角形不仅可能造成超出所需的顶点着色计算，还会产生更多仅部分覆盖的四像素块，带来额外工作。更重要的是，只覆盖少量像素的带纹理网格，线程占用率往往很低。如第 3.10 节所述，纹理采样耗时很大，GPU 通过切换去执行其他片元的着色器程序来隐藏这段时间，等到纹理数据取回后再返回。低占用率会使延迟隐藏效果变差。使用大量寄存器的复杂着色器，也会因为同一时刻可用线程更少而降低占用率（第 23.3 节）。这种情况称为高寄存器压力。还存在其他细微因素，例如频繁切换到其他 warp，可能导致更多缓存未命中。Wronski [1911, 1914] 讨论了各种占用率问题和解决办法。

首先，应使用原生纹理与像素格式，也就是图形加速器内部使用的格式，以避免可能代价高昂的格式转换 [278]。另外两种纹理相关技术，是只加载需要的 mipmap 层级（第 19.10.1 节），以及采用纹理压缩（第 6.2.6 节）。一如既往，纹理越小、越少，内存占用越低，进而传输与访问耗时越少。纹理压缩也能提高缓存性能，因为同样大小的缓存可以容纳更多像素。

一种细节层次技术，是根据对象与观察者的距离，采用不同的像素着色器程序。例如，场景中有三个飞碟模型，最近的飞碟可以使用精细的凹凸贴图表现表面细节，而较远的两个则不需要。最远的飞碟还可以简化或完全去掉镜面高光，既简化计算，也减少“萤火虫”，即欠采样造成的闪烁伪影。在简化模型上使用逐顶点颜色，还有一个额外好处：不会因纹理变化而需要改变状态。

只有当三角形光栅化时片元可见，才会调用像素着色器。GPU 的 early-z 测试（第 23.7 节）将片元的 z 深度与 z 缓冲区比较。如果不可见，片元直接被丢弃，不执行任何像素着色器计算，从而节省大量时间。像素着色器虽然可以修改 z 深度，但这样就无法进行 early-z 测试。

为了理解程序行为，尤其是像素处理阶段的负载，将深度复杂度可视化很有帮助。深度复杂度就是覆盖一个像素的表面数量。图 18.5 给出了例子。生成深度复杂度图像的一种简单方法，是禁用 z 缓冲，并使用类似 OpenGL 的 `glBlendFunc(GL_ONE, GL_ONE)` 调用。首先将图像清为黑色，再以颜色 (1/255, 1/255, 1/255) 渲染场景中的全部对象。这一混合函数设置的作用是：每渲染一个图元，被写入的像素值就增加一个强度等级。因此，深度复杂度为 0 的像素是黑色，深度复杂度为 255 的像素是纯白色，即 (255, 255, 255)。

因此，过度绘制不一定像看起来那么糟，但我们仍希望尽量减少它，又不花费太多 CPU 时间。将场景中的不透明对象粗略排序，再按大致从前到后（由近及远）的顺序绘制，是减少过度绘制的常用方法 [240, 443, 488, 511]。之后绘制的被遮挡对象不会写入颜色缓冲区或 z 缓冲区，也就是减少了过度绘制。此外，像素片元甚至在到达像素着色器程序之前，就可以被遮挡剔除硬件拒绝（第 23.5 节）。有许多方法可以实现排序。一种简单方法是，根据所有不透明对象的质心沿观察方向的距离进行显式排序。如果已经用包围体层次结构或其他空间结构进行视锥体剔除，就可以优先遍历较近的子节点，并沿着层次结构继续这样处理。

对于像素着色器程序复杂的表面，另一种技术可能很有用。执行 z 预通道时，先只将几何体渲染到 z 缓冲区，然后正常渲染整个场景 [643]。这可以消除过度绘制造成的所有着色器计算，但代价是必须对全部几何体额外完整处理一次。Pettineo [1405] 写道，他们团队在电子游戏中使用深度预通道，主要就是为了避免过度绘制。不过，按大致从前到后的顺序绘制，可能不需要这项额外工作就能获得大部分相同收益。一种混合方法，是识别并优先绘制少量大型、简单、最可能带来收益的遮挡体 [1768]。正如 McGuire [1177] 所说，对于他的特定系统，完整绘制的预通道没有改善性能。只有测量，才能知道哪项技术对你的应用最有效，或者这些技术是否有效。

前面建议按着色器和纹理分组，尽量减少状态改变；这里则讨论按距离排序后渲染对象。这两个目标通常产生不同的对象绘制顺序，因此彼此冲突。对于给定场景和视点，总有某个理想绘制顺序，但很难预先找到。也可以采用混合方案，例如将附近对象按深度排序，其余对象按材质排序 [1433]。一种常见而灵活的解决办法 [438, 488, 511, 1434, 1882]，是为每个对象创建排序键，给每项相关标准分配一组位，将它们全部封装进去，见图 18.6。

![图18.6 绘制顺序排序键](https://raw.githubusercontent.com/ahuibo/Real-Time-Rendering-4th-CN/main/Real-Time_Rendering_4th_%E4%B8%AD%E6%96%87/assets/fig_18_4_18.6.png)

**图 18.6** 绘制顺序排序键的例子。键按从小到大排序。设置透明位意味着对象透明，因为透明对象要在所有不透明对象之后渲染。对象到摄像机的距离以低精度整数存储。对于透明对象，距离值需要反转或取负，因为我们希望它们按从后到前的顺序排列。每个着色器都有唯一标识号，纹理也是如此。

我们可以优先按距离排序，但通过限制保存深度的位数，使处于某一距离范围内的对象仍能按着色器分组。仅把绘制划入两三个深度分区也很常见。如果一些对象深度相同，使用的着色器也相同，就用纹理标识符排序，从而把使用相同纹理的对象分到一起。

这是一个简单且依赖具体情境的例子。例如，渲染引擎本身可能已经把不透明对象与透明对象分开，因此不需要透明位。其他字段的位数当然也会随预期的着色器、纹理最大数量而变化。可以加入或替换其他字段，例如混合状态字段、z 缓冲区读写字段。最重要的还是架构。例如，移动设备上某些基于分块的 GPU 渲染器，无法从前到后排序中获得任何好处，因此状态排序才是唯一重要的优化项 [1609]。这里的核心思想是：把所有属性放入单个整数键中，就能高效排序，尽可能减少过度绘制和状态改变。

## 18.4.6 帧缓冲区技术

渲染一个场景，常常涉及大量帧缓冲区访问和像素着色器执行。为了减轻缓存层次的压力，一条常见建议是缩小帧缓冲区中每个像素的存储大小。虽然每个颜色通道使用 16 位浮点值可以提供更高精度，但 8 位值只有其一半大小；只要精度足够，访问就会更快。JPEG、MPEG 等许多图像和视频压缩方案，常常对色度进行子采样。由于人类视觉系统对亮度比对色度更加敏感，这样做对视觉的影响往往可以忽略。例如，Frostbite 游戏引擎 [1877] 使用这种色度子采样思想，降低对每通道 16 位图像进行后处理时的带宽成本。

## 18.4.7 合并阶段

确保只在有用时才启用混合模式。理论上，可以为每个三角形都设置 over 合成，无论它透明还是不透明，因为使用 over 的不透明表面会完全覆盖像素中的值。但这比简单的 replace 光栅操作更昂贵，因此值得跟踪使用镂空纹理的对象和带透明度的材质。另一方面，有些光栅操作不会增加成本。例如，使用 z 缓冲区时，在某些系统上同时访问模板缓冲区并不会增加耗时，因为 8 位模板缓冲区值和 24 位 z 深度值保存在同一个字中 [890]。

值得仔细考虑，各种缓冲区应在何时使用或清除。由于 GPU 具有快速清除机制（第 23.5 节），建议始终同时清除颜色和深度缓冲区，因为这能提高这些缓冲区的内存传输效率。

通常应尽可能避免从 GPU 向 CPU 回读渲染目标。CPU 对帧缓冲区的任何访问，都会在返回渲染结果前迫使整个 GPU 流水线排空，使其中的全部并行性丧失 [1167, 1609]。

如果发现合并阶段确实是瓶颈，可能需要重新考虑你的方法。是否可以使用较低精度的输出目标，或许借助压缩？有没有办法重排算法，减轻这一阶段的压力？对于阴影，能否缓存并复用那些没有任何物体移动的部分？

本节讨论了如何通过寻找瓶颈和调整性能，充分利用每个阶段。不过，要警惕反复优化同一个算法的风险：有时采用一种完全不同的技术，可能更有帮助。
