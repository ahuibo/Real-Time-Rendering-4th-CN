# 18.5 多处理

来源：原书书页 805—814（PDF 第 826—835 页），从“18.5 Multiprocessing”开始，至“Further Reading and Resources”之前。全部下级小节及图 18.8—18.12 均收录于此；章末延伸阅读另见《18.99_延伸阅读与资源》。

传统 API 的发展方向，是减少调用次数，让每次调用完成更多工作 [443, 451]。新一代 API——DirectX 12、Vulkan 和 Metal——采用了不同的策略。对于这些 API，驱动程序经过精简，规模尽可能小；状态验证的大部分复杂工作与责任，以及内存分配等其他功能，都转移给了调用它们的应用程序 [249, 1438, 1826]。这种重新设计，在很大程度上是为了尽量减少绘制调用和状态变更的开销；这些开销来自将旧式 API 映射到现代 GPU 的过程。这些新 API 鼓励的另一件事，是使用多个 CPU 处理器来调用 API。

在 2003 年前后，由于散热和功耗等若干物理问题，CPU 时钟频率不断上升的趋势在约 3.4 GHz 处趋于平缓 [1725]。这些限制促成了支持多处理的 CPU：不再提高时钟频率，而是在单颗芯片中放入更多 CPU。事实上，大量小型核心能够提供最佳的单位面积性能 [75]，这也是 GPU 本身如此高效的主要原因。此后，如何编写能够利用并发的高效、可靠程序，一直是一项挑战。本节将介绍在 CPU 核心上高效进行多处理的基本概念，最后讨论图形 API 如何演进，以便让驱动程序内部支持更多并发。

多处理器计算机大体可以分为消息传递架构和共享内存多处理器。在消息传递设计中，每个处理器都有自己的内存区域，处理器之间通过发送消息来交流结果。这类设计在实时渲染中并不常见。共享内存多处理器正如其名：所有处理器共同使用一个逻辑内存地址空间。最常见的多处理器系统使用共享内存，而其中大多数采用对称多处理（symmetric multiprocessing，SMP）设计。SMP 意味着所有处理器都是相同的。多核 PC 系统就是对称多处理架构的一个例子。

这里，我们将介绍两种在实时图形中使用多个处理器的一般方法。第一种是多处理器流水线，也称时间并行；对它的介绍会比第二种更详细。第二种是并行处理，也称空间并行。图 18.8 展示了这两种方法。随后，基于任务的多处理会将这两类并行结合起来：应用程序创建作业，每个作业都可以由一个独立核心领取并处理。

## 18.5.1 多处理器流水线

如前所述，流水线是一种加快执行速度的方法：把一项作业划分成若干可并行执行的流水线阶段。一个流水线阶段的结果会传递到下一个阶段。对于 n 个流水线阶段，理想加速比是 n 倍，而最慢的阶段（瓶颈）决定实际加速比。到目前为止，我们所看到的流水线，都是利用一个 CPU 核心和一个 GPU，使应用程序、几何处理、光栅化和像素处理并行运行。当主机有多个处理器可用时，也可以使用流水线；在这些情况下，它称为多进程流水线或软件流水线。

![图18.8：多处理器流水线与并行处理](https://raw.githubusercontent.com/ahuibo/Real-Time-Rendering-4th-CN/main/Real-Time_Rendering_4th_%E4%B8%AD%E6%96%87/assets/fig_18_5_18.8.png)

**图 18.8。** 使用多个处理器的两种不同方式。上图展示三个处理器（CPU）如何用于多处理器流水线，下图展示在三个 CPU 上并行执行的情况。这两种实现的一个区别是，采用下方的配置可以获得更低的延迟。另一方面，多处理器流水线可能更容易使用。两种配置的理想加速比都是线性的，也就是说，使用 n 个 CPU 可以获得 n 倍的加速。

这里介绍一种软件流水线。它可以有无穷多种变体，具体方法应适应特定应用。在这个例子中，应用程序阶段被划分为三个阶段 [1508]：APP、CULL 和 DRAW。这是粗粒度流水线，意味着每个阶段都相对较长。APP 阶段是流水线的第一个阶段，因此由它控制其他阶段。应用程序开发者可以在这个阶段加入额外代码，例如进行碰撞检测。这个阶段还会更新视点。CULL 阶段可以执行：

- 对场景图进行遍历和层次化视锥剔除（第 19.4 节）。
- 选择细节层次（第 19.9 节）。
- 状态排序，如第 18.4.5 节所述。
- 最后，生成一份包含所有应渲染对象的简单列表；这一步始终执行。

DRAW 阶段接收 CULL 阶段生成的列表，发出列表中的所有图形调用。这意味着，它只需遍历列表，向 GPU 提交工作。图 18.9 展示了使用这条流水线的几种例子。

如果有一个处理器核心可用，那么三个阶段都在这个核心上运行。如果有两个 CPU 核心可用，那么 APP 和 CULL 可以在一个核心上执行，DRAW 则在另一个核心上执行。另一种配置是在一个核心上执行 APP，在另一个核心上执行 CULL 和 DRAW。哪种配置最好，取决于各阶段的工作负载。最后，如果主机有三个核心可用，那么每个阶段都可以在一个独立核心上执行。图 18.10 展示了这种可能性。

![图18.9：多处理器流水线的不同配置](https://raw.githubusercontent.com/ahuibo/Real-Time-Rendering-4th-CN/main/Real-Time_Rendering_4th_%E4%B8%AD%E6%96%87/assets/fig_18_5_18.9.png)

**图 18.9。** 多处理器流水线的不同配置。粗线表示阶段之间的同步，下标表示帧编号。最上方展示单 CPU 流水线。中间和下方展示使用两个 CPU 时两种不同的流水线划分方式。中间的配置让 APP 和 CULL 占用一个流水线阶段，DRAW 占用另一个流水线阶段。如果 DRAW 的工作量远大于其他阶段，这样划分就很合适。下方的配置让 APP 占用一个流水线阶段，其余两个占用另一个阶段。如果 APP 的工作量远大于其他阶段，这种划分就很合适。注意，下面两种配置为 APP、CULL 和 DRAW 阶段提供了更多时间。

这种技术的优点是提高了吞吐量，也就是渲染速度。缺点是，与并行处理相比，其延迟更大。延迟，或称时间延迟，是指从轮询用户动作到产生最终图像所经历的时间 [1849]。不要将它与帧率混淆，帧率是每秒显示的帧数。例如，假设用户正在使用一台无线头戴式显示器。确定头部位置的信息可能需要 10 毫秒才能到达 CPU，随后渲染一帧需要 15 毫秒。那么，从最初输入到显示的延迟就是 25 毫秒。即使帧率为 66.7 Hz（1 ÷ 0.015 秒），如果不进行位置预测或其他补偿，交互仍可能让人感觉迟钝，因为位置变化传送至 CPU 存在延迟。忽略用户交互带来的延迟（这在两种系统中是一个相同的常量）后，多处理器流水线比并行处理的延迟更大，因为前者使用流水线。下一小节将详细讨论：并行处理会将一帧的工作拆分成若干部分，并发执行。

![图18.10：三阶段流水线与重叠执行](https://raw.githubusercontent.com/ahuibo/Real-Time-Rendering-4th-CN/main/Real-Time_Rendering_4th_%E4%B8%AD%E6%96%87/assets/fig_18_5_18.10.png)

**图 18.10。** 上图展示一条三阶段流水线。与图 18.9 中的配置相比，这种配置为每个流水线阶段提供了更多时间。下图展示一种降低延迟的方法：让 CULL 与 DRAW 重叠执行，并在两者之间使用先进先出（FIFO）缓冲。

与主机仅使用一个 CPU 相比，多处理器流水线能够获得更高的帧率，而延迟基本相同，或因同步成本而略有增加。延迟会随流水线阶段数的增加而增加。对于负载均衡良好的应用程序，使用 n 个 CPU 可以获得 n 倍的加速。

一种降低延迟的技术，是在 APP 阶段结束时更新视点，以及其他对延迟敏感的参数 [1508]。这样可以将延迟减少大约一帧。另一种降低延迟的方法，是让 CULL 和 DRAW 重叠执行。这意味着，只要有任何内容准备好可以渲染，CULL 的结果就立刻传给 DRAW。要实现这一点，两个阶段之间必须有某种缓冲，通常采用 FIFO。缓冲为空或已满时，相应阶段会停顿：当缓冲已满时，CULL 必须停顿；当缓冲为空时，DRAW 则因无工作可做而等待。缺点是，状态排序等技术无法再得到同等程度的运用，因为图元一经 CULL 处理完毕就必须渲染。图 18.10 展示了这种降低延迟的技术。

图中的流水线最多使用三个 CPU，各阶段承担特定任务。不过，这项技术绝不限于这种配置：你可以使用任意数量的 CPU，并按任意方式划分工作。关键在于合理划分需要完成的整项作业，使流水线趋于均衡。多处理器流水线技术所需的同步很少，因为它只需要在切换帧时同步。额外的处理器也可以用于并行处理，但那需要更频繁的同步。

## 18.5.2 并行处理

使用多处理器流水线技术的一个主要缺点，是延迟往往会增加。对于飞行模拟器、第一人称射击游戏以及虚拟现实渲染等应用，这是不可接受的。移动视点时，通常希望立即得到响应，也就是在下一帧得到响应；但延迟较长时就做不到。不过，这也取决于具体情况。如果多处理使帧率从延迟为 1 帧的 30 FPS，提高到延迟为 2 帧的 60 FPS，那么多出来的这一帧延迟并不会造成可察觉的差异。

如果有多个处理器可用，也可以尝试让若干段代码并发运行，这可能缩短延迟。为此，程序的任务必须具备可并行性。将算法并行化有几种不同方法。假设有 n 个处理器可用。采用静态分配 [313] 时，把整个工作包，例如遍历一个加速结构，划分为 n 个工作包。随后每个处理器负责一个工作包，所有处理器并行执行各自的工作包。所有处理器都完成工作包后，可能需要合并各处理器的结果。要让这种方法奏效，工作负载必须具有很高的可预测性。

如果不是这种情况，就可以使用能够适应不同工作负载的动态分配算法 [313]。这些算法使用一个或多个工作池。作业生成后就放入工作池。CPU 完成当前作业后，可以从队列中领取一个或多个作业。必须谨慎处理，确保某项作业只能被一个 CPU 领取，同时确保维护队列的开销不会损害性能。作业较大时，维护队列的开销就不那么成问题；但另一方面，如果作业过大，系统失衡也可能造成性能下降，也就是说，一个或多个 CPU 可能因没有工作可做而等待。

与多处理器流水线一样，一个在 n 个处理器上运行的并行程序，理想加速比是 n 倍。这称为线性加速。虽然很少真正达到线性加速，但实际结果有时也能接近它。

书页 807 的图 18.8 同时展示了一条多处理器流水线和一个并行处理系统，两者都使用三个 CPU。暂且假设，它们每帧需要完成的工作量相同，而且两种配置都能达到线性加速。这意味着，与串行执行（也就是在单个 CPU 上执行）相比，其执行速度将提高到三倍。此外，我们假设每帧的全部工作需要 30 ms，这意味着单个 CPU 上的最高帧率约为 1 ÷ 0.03 ≈ 33 帧/秒。

理想情况下，多处理器流水线会将工作分为三个大小相等的工作包，让每个 CPU 负责其中一个工作包。每个工作包应当需要 10 ms 完成。如果沿着流水线跟踪工作流，就会看到流水线中的第一个 CPU 工作 10 ms（即完成作业的三分之一），然后将工作传给下一个 CPU。第一个 CPU 随即开始处理下一帧的第一部分。当一帧最终完成时，完成这一帧总共花费了 30 ms；但由于工作在流水线中并行进行，因此每 10 ms 就有一帧完成。所以，延迟为 30 ms，加速比为三倍（30 ÷ 10），最终达到每秒 100 帧。

同一程序的并行版本也会把作业分为三个工作包，但这三个工作包会在三个 CPU 上同时执行。这意味着延迟为 10 ms，而一帧的工作同样需要 10 ms。由此可见，与多处理器流水线相比，并行处理的延迟要短得多。

## 18.5.3 基于任务的多处理

了解流水线和并行处理技术之后，自然会想到将两者结合到一个系统中。如果只有少数几个处理器可用，那么采用一个简单系统，将各子系统明确分配给某个核心，可能是合理的。但是，鉴于许多 CPU 都有大量核心，发展趋势是采用基于任务的多处理。正如可以为一个能够并行化的过程创建多个任务（也称作业）一样，这一思路还可以扩展到流水线。任何核心生成的任何任务，都会在生成时放入工作池。任何空闲处理器都会领取一个任务进行处理。

将应用程序改为多处理的一种方法，是考察其工作流程，确定哪些子系统依赖其他子系统。见图 18.11。

如果处理器在等待同步时停顿，那么由于这种成本以及任务管理的开销，应用程序的任务化版本甚至可能变得更慢 [1854]。不过，许多程序和算法确实拥有大量可以同时执行的任务，因此能够从中受益。

下一步是确定每个子系统的哪些部分可以分解成任务。一段代码若适合成为任务，通常具有以下特征 [45, 1060, 1854]：

- 任务具有明确定义的输入和输出。
- 任务在运行时是独立且无状态的，并且总能完成。
- 任务不会大到经常成为唯一仍在运行的处理过程。

C++11 等语言内置了多线程支持设施 [1445]。在 Intel 兼容系统上，Intel 的开源 Threading Building Blocks（TBB）是一个高效的库，可以简化任务生成、任务池管理和同步 [92]。

在性能至关重要时，让应用程序创建自身的任务集合，并对它们进行多处理，已是理所当然的做法，例如模拟、碰撞检测、遮挡测试和路径规划等任务 [45, 92, 1445, 1477, 1854]。这里再次指出，有些时候 GPU 核心也往往处于空闲状态。例如，在生成阴影贴图或执行深度预处理通道时，它们通常没有得到充分利用。在这些空闲时段，可以用计算着色器执行其他任务 [1313, 1884]。视架构、API 和内容而定，有时渲染流水线无法让所有着色器都保持忙碌，这意味着始终有一部分资源可用于计算着色。我们不讨论如何优化这些工作，因为 Lauritzen 提出了有说服力的论点：由于硬件差异和语言限制，无法编写既快速又可移植的计算着色器 [993]。下一小节的主题是如何优化核心渲染流水线本身。

## 18.5.4 图形 API 对多处理的支持

并行处理往往无法直接适应硬件约束。例如，DirectX 10 及更早版本一次只允许一个线程访问图形驱动程序，因此，要对实际的绘制阶段进行并行处理就比较困难 [1477]。

图形驱动程序中有两类操作可能使用多个处理器：资源创建和与渲染有关的调用。创建纹理和缓冲区等资源，可以完全是 CPU 端操作，因此天然适合并行化。不过，创建和删除也可能是阻塞任务，因为它们可能触发 GPU 上的操作，或者需要某个特定的设备上下文。无论如何，旧式 API 的诞生早于消费级多处理 CPU，因此需要重新编写，才能支持这种并发。

这里使用的一个关键构造是命令缓冲区或命令列表，其渊源可以追溯到 OpenGL 中一个称为显示列表的旧概念。命令缓冲区（command buffer，CB）是一份 API 状态变更调用和绘制调用的列表。这些列表可以按需创建、存储和重放，也可以组合起来，形成更长的命令缓冲区。只有一个 CPU 处理器通过驱动程序与 GPU 通信，因此它可以将 CB 发送给 GPU 执行。不过，每个处理器（包括这个负责通信的处理器）都可以并行地创建或串接已存储的命令缓冲区。

![图18.12：命令缓冲区](https://raw.githubusercontent.com/ahuibo/Real-Time-Rendering-4th-CN/main/Real-Time_Rendering_4th_%E4%B8%AD%E6%96%87/assets/fig_18_5_18.12.png)

**图 18.12。** 命令缓冲区。每个处理器使用自己的延迟上下文（橙色），创建并填充一个或多个命令缓冲区（蓝色）。每个命令缓冲区都会发送到进程 #1，由该进程使用自己的立即上下文（绿色）按需执行。进程 #1 在等待来自进程 #3 的命令缓冲区 N 时，可以执行其他操作。（据 Zink 等人 [1971] 改编。）

例如，在 DirectX 11 中，与驱动程序通信的处理器会将渲染调用发送到所谓的立即上下文（immediate context）。其他处理器各自使用一个延迟上下文（deferred context）生成命令缓冲区。顾名思义，这些命令不会直接发送到驱动程序，而是发送到立即上下文进行渲染。见图 18.12。另一种做法是将一个命令缓冲区发送到另一个延迟上下文，由后者将其插入自己的 CB。除了将命令缓冲区发送到驱动程序执行之外，立即上下文能够执行而延迟上下文不能执行的主要操作，是 GPU 查询和数据回读。除此之外，从这两类上下文来看，命令缓冲区的管理方式相同。

命令缓冲区及其前身——显示列表——的一个优点，是可以存储并重放。命令缓冲区在创建时并未完成全部绑定，这有助于复用。例如，假设某个 CB 包含一个观察矩阵。相机移动了，观察矩阵也随之变化。不过，观察矩阵存储在常量缓冲区中。CB 并不存储常量缓冲区的内容，只存储对它们的引用。因此，可以更改常量缓冲区的内容，而无须重建 CB。要确定如何最好地提高并行性，就需要为命令缓冲区的创建、存储和组合选择合适的粒度——按视图、按对象，还是按材质 [1971]。

在命令缓冲区成为现代 API 的一部分之前，这类多线程绘制系统就已经存在多年 [1152, 1349, 1552, 1554]。API 支持使这一过程更简单，也使更多工具能够配合所创建的系统工作。然而，命令列表确实会带来创建和内存成本。此外，如第 18.4.2 节所述，在 DirectX 11 和 OpenGL 中，将 API 的状态设置映射到底层 GPU，仍是一项开销很大的操作。在这些系统中，当应用程序是瓶颈时，命令缓冲区可能有帮助；但当驱动程序是瓶颈时，它们可能适得其反。

这些较早的 API 中，某些语义不允许驱动程序将各种操作并行化，这推动了 Vulkan、DirectX 12 和 Metal 的开发。这些较新的 API 采用精简的绘制提交接口，能够很好地映射到现代 GPU，从而最大限度地降低驱动程序成本。命令缓冲区管理、内存分配和同步决策，都从驱动程序的责任变成应用程序的责任。此外，在这些较新的 API 中，命令缓冲区在形成时只验证一次，所以重复重放的开销比 DirectX 11 等较早 API 使用的命令缓冲区更低。所有这些因素共同提高了 API 效率，实现了多处理，并减少了驱动程序成为瓶颈的可能性。
